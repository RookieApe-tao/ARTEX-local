# 交付报告生成机制改进

## 目标

让开发能快速看清漏洞成立条件、最短复现方法、实际影响和修复办法。详细报告保留完整台账；交付报告减少重复记录，只留下处理漏洞所需的信息。

## 生成流程

- Reporter 先读漏洞节点、执行记录和原始证据，再整理成立条件、实际操作、观察结果、未验证影响和材料位置。旧报告与 worker 总结只作线索，不作结论依据。
- 默认草稿入口由 Reporter 根据原始材料一次生成报告，并在同一次生成中自查事实边界和固定结构；Agent 仍通过 `report_finding → Reporter → update_finding_report` 写入报告。
- `update_finding_report` 不增加模型调用，只执行固定结构、CVSS 向量和证据版本校验，再由平台附加完整流量原文并一次保存详细报告与交付报告。格式错误或证据版本变化时拒绝保存；详细报告不经交付报告写作规则改写。
- 默认提示词、触发消息、工具说明和兼容草稿入口保持一致；启动迁移仅更新已知旧默认，保留用户修改内容。
- 同次自查不增加模型调用，但仍不能保证模型判断正确；离线样本和人工验收用于发现事实、表达及结构问题。

## 固定报告结构

```markdown
# <系统或模块> <功能或接口> <缺陷>：<实际影响>

CVSS 4.0：<完整 Base 向量> 评分 <分数>（<等级>）

## 描述
<问题、成立条件和实际业务结果>
### 定级依据
<权限条件及已观察影响如何支持评分>

## 修复建议
<针对已确认问题的修复办法和预期行为>

## 测试过程
### 发现过程与攻击思路
<最短复现步骤、必要账号或条件、关键请求或命令及判据>
### 失败尝试与未验证项
<影响结论的实际失败和未验证边界>
### Burp 复现
<HTTP 测试说明 Burp Repeater 的实际使用情况；非 HTTP 说明不适用>

## 攻击链路
~~~text
<入口或已知起点>
└─ <请求或命令>
   └─ <观察到的结果>
~~~

## 证据说明
<材料来源、完整性和缺失内容>
### 复测标准
<修复成功时可观察到的结果>
```

## 内容边界

- 测试时间以北京时间显示；仅当先后顺序、竞态或有效期影响结论时，在交付正文保留准确时间。完整时间、工具参数、失败日志、哈希和证据索引放在详细报告。
- 交付报告不要求每次重复列出工具和时间字段。只写最短复现需要的账号、请求或命令、关键参数、顺序和判据；材料没有记录的内容不补造。
- 失败尝试只引用真实执行记录。没有找到撤销工具不能推断为无法恢复；只有文件信息或响应头不能推断已取得内容或已验证权限。
- Burp Repeater 的实际使用情况写在测试过程。HTTP 未使用 Burp 时给出标记为未验证的建议复测步骤；非 HTTP 写实际命令并说明 Burp 不适用。串行重放不能证明并发。
- 攻击链只保留已知功能来源、关键请求或命令及实际结果。页面来源未知时从接口开始，不补造前端操作。
- 已绑定的 HTTP 请求和响应由 ARTEX 原文附加在末尾，正文只引用一次。平台外材料只有在完整留存时才可引用；路径、片段或缺少正文时说明缺口。
- 合成样本明确说明未测试真实目标。身份标记不代表认证凭证。

## 保存校验

保存前检查报告头、固定章节及子标题、CVSS 向量一致性、攻击链结构和证据版本/完整性。保存校验不使用关键词列表评判文风或语义，不硬截断正文、不改写附加的原始证据。

调用仍沿用 `report_finding → Reporter → update_finding_report`，工具名、参数和一次保存两份报告的方式不变。历史报告不批量改写；默认值迁移只处理与已知旧默认完全一致的内容。
