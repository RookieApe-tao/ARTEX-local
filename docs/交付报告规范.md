# 交付报告规范

交付报告属于单个漏洞，面向开发修复和业务复核。报告应让接收者看清测试前提、实际操作、业务结果、影响边界和修复办法，并能根据证据重复验证。

报告继续由 `report_finding` 登记漏洞后自动触发的报告 Agent 撰写，与详细报告通过一次 `update_finding_report` 保存。调用方式不变，不增加人工审批步骤。

## 详细报告与交付报告

详细报告保留逐项测试台账：工具、参数、账号条件、时间、判据、实际观察、失败尝试和证据位置。需要逐步追查测试过程时，使用这份台账。

交付报告用于理解问题、复现和修复。正文说明漏洞如何发现、必要前提、实际影响和修复办法；测试过程保留能重复验证结论的最短步骤。相关失败和限制简短说明，完整记录引用详细报告。原始请求与响应放在末尾，不在描述、测试步骤和攻击链中重复粘贴。

同一个报告 Agent 先从现有证据整理事实，再撰写两份报告并自查。交付正文按用途说明材料，例如“正常查询”“修改后的请求”“操作后的查询结果”。内部编号保留在详细台账和原始元信息中。实际结果和潜在影响分开写；未复现的内容写“未验证”。

## 固定报告结构

报告头只保留一个一级标题和一行 CVSS 4.0 信息。一级标题就是漏洞名称，不另写“漏洞名称”字段；向量、分数和等级只出现一次。交付报告的测试时间集中写一次，写成北京时间。竞态、有效期或先后顺序影响结论时，相关步骤再给出必要的精确时间；逐请求原始时间保留在详细报告和证据中。缺少时间记录时写“未记录”，不拿文件修改时间代替。

新报告固定使用下列五个二级标题和必需的三级标题。旧报告继续按原文展示，不会自动改写；重新保存时须符合当前格式。

| 二级标题 | 必需内容 |
| --- | --- |
| 描述 | 简短说明权限、利用条件、受影响功能、实际操作和业务结果；必须含“定级依据”。 |
| 修复 | 写证据支持的服务端改动及预期行为，不猜源码位置和版本。 |
| 测试过程 | 必须含“发现过程与攻击思路”“失败尝试与未验证项”；简述发现依据，给出能复现结论的最短步骤、必要参数和判据。HTTP 测试须给出 Burp Repeater 复现步骤。完整工具记录留在详细报告。 |
| 攻击链路 | 用简短树形文本交代实际入口、身份条件、请求、服务端处理和业务结果。树形内容放在 `text` 代码块内；接口路径单独成行。未知页面不能补造为前端操作。 |
| 证据说明 | 必须含“Burp 复现”“复测标准”；交代材料来源和用途，末尾保留成对的完整请求与响应。 |

结构示例只规定排版，不代表已经取得证据：

```markdown
# <系统>-<模块> <接口或功能> <缺陷>：<实际复现的业务后果>

CVSS 4.0：<完整 Base 向量>  评分 <分>（<等级>）

## 描述
<权限、条件、操作、业务结果；按报文用途说明依据>
### 定级依据
<说明权限、交互条件和已观察影响如何支持评分；缺少依据时写明待复核>

## 修复
<对应根因的服务端改动和修复后的预期行为>

## 测试过程
测试时间：<真实测试时间范围>（北京时间）
### 发现过程与攻击思路
<用简短文字说明线索来源和确认问题的关键观察>
<按实际顺序写出最短复现步骤，只保留复现必需的身份条件、参数和结果判据>
<说明如何在 Burp Repeater 重放，以及如何判断结果；完整请求在本报告末尾>
### 失败尝试与未验证项
<概括与结论有关的失败尝试、未完成测试和影响范围；完整记录留在详细报告>

## 攻击链路
~~~text
<实际入口：已核对页面或业务操作，或脚本/接口调用>
└─ <所用身份、必要条件和实际请求动作>
   └─ <METHOD> <path>
      └─ 服务端<实际处理和响应>
         └─ <后续操作或业务影响>
~~~
<在图前或图后按用途集中说明依据；缺失环节写“未验证”>

## 证据说明
<每份材料的来源、账号和用途名称；必要的精确时刻保留在原始元信息中>
### Burp 复现
<指出末尾完整请求的位置和实际 Burp 重放状态；测试过程已写的步骤不重复，非 HTTP 说明不适用>
### 复测标准
<复测操作及通过/失败判据>
<成对的完整请求与响应，分别使用独立 http 代码块>
```

格式校验在 Agent 工具和 HTTP 保存入口执行。缺少一级标题、CVSS 向量与参数不一致、章节和必需子标题缺失或顺序错误、章节无内容、攻击链没有起点和分支的 `text` 树形图、代码块或 HTML 注释未闭合时，保存会返回错误。正文不按字数或词语黑名单拦截；格式通过也不证明结论真实，仍须核对原始记录。

## 测试记录与结论

详细报告的每个测试项写清名称、时间和时区、账号权限、前置条件、工具及版本、实际命令或脚本参数、判据、响应和业务结果、结论及证据索引。交付报告只保留复现必要条件、关键操作和结果；工具版本、完整参数、逐次记录、内部编号、哈希和索引留在详细台账及材料元信息，除非它们是复现条件。

发现过程说明真实线索来自哪里，以及为什么采用后续测试方式。只有已核对的页面或操作才能写成用户路径；若证据只来自接口、脚本或工具记录，就从这个实际入口说明发现过程。页面、前端请求关系或服务端源码未检查时明确说明，不补造界面操作、前端行为或内部实现。

没有复现的结论写“未验证”。未执行、执行失败和未复现分别说明原因；不能把没有测成写成没有问题。失败请求、命令错误、超时和权限拒绝应保留，同类重复失败可以汇总次数并引用代表记录。没有取得失败材料时写“未取得失败尝试记录”，不能补造一次失败。

HTTP 200 不能单独证明业务操作成功。重复提交类问题应分别记录实发请求数、业务成功数、新增记录数和不同记录 ID 数；查询条件保持一致，差分写为测试后数量减去测试前数量。客户端同步放行不能证明服务端同时处理。

## 证据与 Burp 复现

原始材料可能来自 ARTEX-Pro 已绑定流量，也可能来自本机 socket、curl、脚本或其他采集记录。必须说明真实来源，不因域名或时间相近便把其他账号的流量作为本次证据。原始请求、响应缺失时说明缺失，不能根据摘要补包。

平台将全部已绑定请求与对应响应成对附在“证据说明”内。每个 `http` 代码块只包含一条留存报文，绑定编号、源流量 ID、请求地址和真实采集时间放在围栏外的原始元信息中。正文和报文标题按用途说明，例如“正常查询”“修改后的请求”“操作后的查询结果”，不要求读者来回查找内部编号。重存会替换旧的自动附录，留存事实和原包不改写。

平台留存头部经过采集整理，不等于逐字节网络抓包。为 Burp 整理请求时，应说明 HTTP 版本或传输格式的转换，不能称为原始报文。二进制正文以 Base64 展示时，必须还原字节后才能重放；缺失报文头时也不能声称直接粘贴即可复现。

“测试过程”中的 Burp Repeater 说明应给出末尾完整请求的位置、复现必需的账号或会话、关键参数、发送顺序及判据。并发设置只有在影响复现时才需说明。没有实际在 Burp 重放过时注明“Burp 复测未验证”。命令或 curl 不能替代应交付的 HTTP 请求包。

非 HTTP 漏洞在测试过程中注明“Burp Repeater 不适用：非 HTTP”，提供对应工具的完整命令、输入和判据，不为填模板伪造 HTTP 报文。

附包继续执行完整正文长度和哈希校验。绑定报文累计超过 4 MiB、文件缺失或完整性不符时，保存明确失败，不截取片段冒充完整包。更多绑定与导出说明见[漏洞多流量证据](漏洞流量证据.md)。

## 评分、迁移与历史报告

CVSS 向量根据证据填写，权限、用户交互、特殊条件和影响均应给出依据。没有可信计算结果时写“待计算”。详情页根据保存的完整向量在前端本地计算评分和等级。旧报告展示时会合并重复的漏洞名称和 CVSS 信息；正文不会自动改写。

默认 Reporter 仅在提示词与已知旧版完全一致时升级，用户自定义提示词保留。具备 `update_finding_report` 权限的 Agent 在运行时都会收到同一份写作和保存规范，流量绑定开关不影响这份规范。默认提示词、触发消息、工具说明和兼容草稿接口使用相同章节和事实边界。

已有报告不会自动重写，重新生成并保存后才应用当前写作要求。固定章节和保存校验只能约束结构，报告结论、证据对应关系和复现步骤仍须由测试人员逐项核对。
