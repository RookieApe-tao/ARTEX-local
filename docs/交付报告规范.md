# 交付报告规范

交付报告面向开发和业务人员，说明问题、复现方法、实际影响和修复办法。详细报告留存完整测试台账；交付报告只保留读者理解和处理问题所需的信息。

## 固定结构

```markdown
# <系统或模块> <功能或接口> <缺陷>：<实际影响>

CVSS 4.0：<完整 Base 向量> 评分 <分数>（<等级>）

## 描述
<问题、成立条件和实际业务结果>
### 定级依据
<权限条件及已观察影响如何支持评分>

## 修复建议
<针对已确认问题的修复办法和预期行为>

## 测试过程
### 发现过程与攻击思路
<最短复现步骤、必要账号或条件、关键请求或命令及判据>
### 失败尝试与未验证项
<影响结论的实际失败和未验证边界>
### Burp 复现
<HTTP 测试说明 Burp Repeater 的实际使用情况或未验证的复测步骤；非 HTTP 写明不适用>

## 攻击链路
~~~text
<入口或已知起点>
└─ <请求或命令>
   └─ <观察到的结果>
~~~

## 证据说明
<材料来源、完整性和缺失内容>
### 复测标准
<修复成功时可观察到的结果>
```

## 写作要求

- 用简短、常见的中文说明实际情况。先写问题和业务结果，删除重复台账、内部流程标签和不必要的背景。
- 结论以原始报文、命令输出和执行记录为依据。旧报告和 worker 总结只用于找线索；没有记录的账号、工具、页面入口、失败尝试或影响不补造。
- 详细报告保留工具参数、逐项时间、失败日志、哈希和证据索引。交付报告只写复现必需的账号、请求或命令、操作顺序和判据。
- 日期和时间以北京时间展示。仅当先后顺序、竞态、令牌有效期等影响结论时，在交付正文保留准确时间；其他时间留在详细报告。原始报文和日志保持原样。
- 描述区分已观察结果与未验证影响。状态码、响应头或身份标记不能单独证明未授权访问或数据泄露；响应正文缺失时说明缺口。
- 修复建议针对已确认问题。没有源码或配置证据时，不猜文件、版本和具体实现。没有找到撤销操作不等于无法恢复；返回文件信息不等于已验证文件内容。
- 攻击链只连接证据支持的入口、必要条件、请求或命令和实际结果。页面来源未知时从接口开始，不补造前端操作或服务端实现。
- HTTP 问题在“测试过程”说明 Burp Repeater 的实际使用情况。未使用时，标明复测未验证并给出建议步骤；并发问题不得用 Repeater 串行重放证明并发。非 HTTP 问题写实际命令，并说明 Burp 不适用。
- 完整绑定的 HTTP 请求和响应由 ARTEX 原文附加在报告末尾，正文只引用一次用途。平台外报文只有在完整留存时才按真实来源引用；只有路径、片段或缺少响应正文时说明材料缺口。
- 合成样本说明未测试真实目标。合成身份标记不代表真实认证凭证。

## 保存与评审

Reporter 仍由 `report_finding` 触发，通过现有 `update_finding_report` 一次保存详细报告和交付报告。保存校验检查标题、固定章节与子标题、攻击链结构、CVSS 向量一致性、证据版本和完整性；不通过关键词列表判断文风或语义，不自动截断或改写原始证据。

默认提示词迁移只更新与已知旧默认完全相同的内容，保留用户自定义提示词。历史报告不会被自动覆盖。固定样本覆盖越权、注入、并发、登录会话、非 HTTP 和证据不完整场景；格式测试不替代对模型样稿的逐份阅读。

评测方法见 [报告评测](../tools/report-eval/README.md)。
