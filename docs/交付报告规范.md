# 交付报告规范

交付报告面向开发和业务人员，用来说明问题、复现方式、实际影响和修复办法。详细报告保留完整测试记录；交付报告只写读者判断和处理问题所需的信息。

## 固定结构

报告使用一个漏洞名称标题、一行 CVSS 4.0 信息和以下五节。章节顺序固定，不增加子标题。

```markdown
# <系统或模块> <功能或接口> <缺陷>：<实际影响>

CVSS 4.0：<完整 Base 向量> 评分 <分数>（<等级>）

## 描述
<问题、权限条件、实际结果和定级依据>

## 修复建议
<针对已确认根因的修复和预期行为>

## 测试过程
测试时间：<YYYY-MM-DD HH:mm:ss（北京时间）；没有记录时写“未记录”>
执行工具：<实际工具；没有记录时写“未记录”>
<账号或会话、参数、步骤、结果、判据、失败尝试和未验证事项>
<HTTP 问题逐字写出“Burp Repeater”；未实际使用时标记未验证并给建议步骤。非 HTTP 说明 Burp 不适用。协议未确认时标注未验证，不猜协议或给操作步骤>

## 攻击链路
~~~text
<入口或已知起点>
└─ <请求或命令>
   └─ <观察到的结果>
~~~

## 证据说明
<材料来源、完整性和缺失内容>
```

## 写作要求

- 用短句说明实际情况，避免重复标题、接口清单、内部分析过程和不常见术语。
- 工具、参数、时间、失败结果必须能在本次执行记录中找到。时间统一写北京时间；缺少时间时写“测试时间：未记录”，不补造。
- 工具只从执行记录读取；报文来源不能证明实际使用了什么工具。缺少工具记录时写“执行工具：未记录”。
- HTTP 报告在“测试过程”逐字写出 Burp Repeater，并说明实际使用状态、必要会话、请求修改项和判据。未实际使用时写“Burp Repeater 未实际使用，复测未验证”，并把复现步骤标为建议。不要编造 Repeater 功能；串行重放不能证明并发。
- 没有足够证据判断协议时，写“协议未确认，Burp Repeater 复测未验证”，不要猜协议，也不要给 Repeater 操作步骤。
- 非 HTTP 问题写实际命令、输入和结果，只说明 Burp 不适用，不提 Repeater。
- 合成身份标记不是认证凭证。不要把标记写成真实身份，也不要建议替换标记；复测应从获授权账号正常登录后重新捕获请求。
- CVSS 向量、分数和等级只出现在报告头。描述中用一句话说明定级依据。
- 已绑定 HTTP 请求和响应由 ARTEX 附在报告末尾，正文按用途引用，不重复粘贴。非 HTTP 问题不能写成附有 HTTP 报文。材料缺失时说明缺口；HTTP 状态码不能单独证明业务操作成功。
- 修复建议对应已确认的问题。未检查源码或配置时，不猜文件路径、版本和具体实现。
- 合成样本要说明没有测试真实目标。潜在影响与实际观察分开描述。
- 只有状态码、响应头或身份标记时，不据此认定未鉴权或数据泄露；响应不完整时先写证据缺口。
- 重复写入优先给唯一约束或幂等处理。修复建议只给有证据支持的一种低改动方案；证据不足时先要求补证。
- SQL 注入优先使用参数化查询，不建议用转义或拒绝特殊字符代替。
- 不使用“判决项”“归属对照”“人工执行”“测试侧无删除通道”“阴性结果”“零错配”“如实交付”“W07”“属主”“存在性哨兵”“公开投影”等内部标签或实验记录用语。
- 保存校验会拒绝上述内部用语、逐位读取类结论，以及关键字过滤式 SQL 修复建议；草稿生成后仍需核对实际证据。

## 保存与历史报告

Reporter 沿用现有 `report_finding`、`update_finding_report` 流程，一次保存详细报告和交付报告。保存校验检查章节、CVSS 和攻击链格式，不按正文词语拦截。

升级时只迁移与已知默认提示词完全相同的内容；用户修改过的提示词保留。历史报告不会自动重写，重新生成并保存后才使用当前格式。

固定样本和离线评测说明见 [报告评测](../tools/report-eval/README.md)。样本仅用于本地写作评估，不访问真实目标。
